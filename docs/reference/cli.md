# CLI Command Reference

The `sdkt-cli` crate uses `clap` (derive API) for command routing. Every command returns `Result<(), Box<dyn std::error::Error>>`; library errors (`RpcError`, `DecodeError`, `WasmError`) bubble up and are printed via `eprintln!` with a non-zero exit.

## Command Tree

```text

├── decode <xdr>
│   ├── --type <ScVal|TransactionEnvelope|TransactionResult|ContractEvent>
│   ├── --format <json|pretty>
│   ├── --file <path>
│   ├── --abi <wasm>                  (ABI-aware decode from a local WASM)
│   └── --abi-contract <id>           (ABI-aware decode using deployed contract's on-chain WASM)

├── encode <TYPE:VALUE>...
│   │   (fully offline: encode typed values to base64 XDR)
│   │   Supports: u32, i32, u64, i64, timepoint, duration, u128, i128, bool,
│   │   string, symbol, bytes, address. Also json:<JSON> for composite values.

├── inspect <contract-id>
│   ├── --interface                 (render full interface instead of name-only ABI)
│   ├── --format <json|pretty>
│   ├── --abi <wasm>                (ABI-aware storage decode)
│   └── --abi-contract <id>         (fetch deployed contract's ABI)

│   ├── analyze <contract-id> [--abi <wasm>] [--abi-contract <id>] [--format]
│   ├── estimate <wasm-path>  [--ledgers <N>] [--format <pretty|json>]
│   ├── storage-diff --old <snapshot-a.json> --new <snapshot-b.json> [--extend-plan] [--format <pretty|json>]
│   ├── read --contract <contract-id> --key-xdr <BASE64_XDR> [--abi <wasm>] [--format]
│   ├── extend --contract <contract-id> --ledgers <N> [--key <xdr>]... [--identity <name>] [--timeout <s>] [--interval <s>] [--format]
│   └── restore --contract <contract-id> --envelope <xdr> [--dry-run] [--identity <name>] [--timeout <s>] [--interval <s>] [--format]
│
│   `estimate` performs an offline calculation of storage rent over a specified
│   ledger horizon (default 17,280 ledgers, ~1 day) using the contract spec ABI.
│   It computes a breakdown across Instance, Persistent, and Temporary classes
│   and a total in stroops and XLM.
│
│   `storage-diff` compares two storage snapshots (`--old` and `--new`, generated by
│   `sdkt storage analyze --format json`) and identifies removed, expiring, and unchanged
│   entries. With `--extend-plan`, it derives a non-mutating remediation plan (target contract,
│   affected keys, and suggested ledger horizon) for operator extension. The plan splits
│   actionable entries by class: `ExpiringSoon` entries are extendable and appear in the
│   ready-to-run `sdkt storage extend` command; `Removed` entries are gone from the ledger
│   and cannot be extended — the plan names `sdkt storage restore` and the invocation
│   envelope it needs instead, and never includes a removed key in an extend command.
│   A removed-only plan therefore prints no extend command at all. In JSON output the
│   plan keeps the legacy `keys` (all actionable keys), `suggested_ledgers`, and
│   `suggested_ledgers_reason` fields and adds `extendable_keys` and `removed_keys`.
│
│   Snapshots recorded by `sdkt storage analyze --format json` include capture context:
│   - `latest_ledger`: the ledger sequence at capture time.
│   - `network`: the network identity (passphrase or network name) against which capture was performed.
│
│   When diffing snapshots:
│   - If both snapshots record a network and they differ, the diff is refused with an error
│     naming both networks (preventing cross-network skew from reading as state drift).
│   - If both snapshots record a ledger, TTLs are compared on a common basis by normalising
│     the old snapshot's TTLs by the ledger delta (`new_ledger - old_ledger`), ensuring normal
│     time passage between snapshots does not falsely classify entries as expiring soon.
│     The ledger delta is surfaced in both pretty and JSON output.
│   - Backward compatibility: legacy snapshot files omitting capture context remain fully
│     supported; their capture context is reported as "unknown".
│   - Value drift detection: `sdkt storage analyze --format json` records each entry's
│     base64 XDR `ScVal` value. When two snapshots both carry values for the same entry,
│     `storage-diff` reports a `value_changed` delta (before/after values) instead of
│     classifying the entry as unchanged. An entry whose value and TTL both match stays
│     unchanged; TTL-only changes still report only TTL/rent deltas. Entries without
│     captured values (legacy snapshots, contract-code entries) are never flagged for
│     value drift.
│
│   `read` fetches a single ledger entry by its complete `LedgerKey` (base64 XDR).
│   The instance key is NOT included automatically — supply the full key via --key-xdr.
│   ABI formatting is optional and applies only to the returned value.
│
│   `extend` submits an `ExtendFootprintTtl` transaction. The contract instance
│   key is always included in the read-only footprint. Additional `--key` values
│   (base64 XDR or hex XDR) are merged and de-duplicated. This does NOT discover
│   all contract storage and does NOT restore archived entries.
│
│   `analyze` (alias `snapshot`) accepts repeatable `--key-xdr` (alias `--key`). Each
│   `getLedgerEntries` request is limited to 200 keys; larger read sets (including
│   the automatically included instance key) are fetched in sequential batches.
│   For batched reads, found entries retain request order and absent entries are
│   omitted. A failed batch or a change of ledger between batches fails the
│   complete read; retry if the ledger changes. This batching applies to reads,
│   not to the transaction footprint limits of `extend` or `restore`.
│
│   `restore` simulates `--envelope` (the invocation that failed on archived
│   state), adopts the `restorePreamble` footprint and minimum resource fee, and
│   submits a `RestoreFootprint` transaction. It fails without submitting when
│   the simulation has no preamble (state is live) or the preamble footprint is
│   empty or malformed. `--dry-run` prints the keys and fee without signing or
│   submitting. It restores only; re-run the invocation afterwards.
│
│   `--abi <wasm>` supplies the ABI from a local WASM; `--abi-contract <id>` fetches
│   the deployed contract's on-chain WASM and uses it as the ABI source
│   for storage decoding. The two flags are mutually exclusive.
│
├── invoke <CONTRACT_ID> <FUNCTION>
│   ├── --args <TYPE:VALUE>...    (same typed-args as `call` / `tx build`;
│   │                            strict: unknown types are rejected)
│   ├── --identity <name>        (signs and pays; default: "default")
│   ├── --timeout <SECONDS>      (wait-for-settlement timeout; default 60)
│   ├── --interval <SECONDS>     (poll interval while waiting; default 1)
│   ├── --format <json|pretty>
│   └── --network-profile <NAME> / --rpc-url <URL> / --network-passphrase <P>
│
│   Polling rules (shared by every command that waits for a transaction):
│   `--interval` must be greater than 0 and `--timeout` must be greater than
│   or equal to `--interval`; invalid pairs are rejected before any network
│   or identity work begins. `--no-wait` returns the transaction hash right
│   after submission and ignores both flags.
│
│   State-changing end-to-end flow in one command:
│     fetch account sequence → simulate → build final envelope (authoritative
│     footprint + fees + auth entries from simulation) → sign with the local
 main
│   Result decoding is limited to the transaction-level `TransactionResult`
│   XDR (auto-detection also recognizes `ScVal`, `TransactionEnvelope`,
│   `TransactionResult`, and `ContractEvent`; there is no XDR
│   `TransactionStatus` type in the pinned `stellar-xdr` 28.0.0 API).
│   Inherits the mainnet safety guard

│

### Verifying the lock

`sdkt lock verify` answers one question — is `sdkt.lock` consistent with what is on
disk? — and its outcome is consumed as a verdict, so the three states are kept
distinct:

- **Consistent** — every locked artifact hash matches, every manifest contract and
  dependency is accounted for, and dependency paths/caches/commits agree. Prints
  `✓ sdkt.lock is consistent with current artifacts` and `✓ package dependencies
  verified`; exits **0**.
- **Absent** — no `sdkt.lock` at all. Advisory (matching the lock's documented
  non-fatal role): prints `⚠ No sdkt.lock found; run `sdkt build` to generate one`
  and, when dependencies are declared, `⚠ No sdkt.lock present; package
  dependencies unverified`; exits **0**.
- **Corrupt** — `sdkt.lock` exists but cannot be parsed. This is a broken build
  input, never a clean bill of health: prints `⚠ Corrupt sdkt.lock: failed to
  parse lock file sdkt.lock: ...` (the same parse-error wording `sdkt lock show`
  uses) and exits **1**.

Drift within a valid lock stays advisory: mismatched artifact hashes, missing
entries, and dependency drift are listed and the command exits 0.

`--format json` emits `{ "present", "consistent", "mismatched",
"missing_in_lock", "error", "dependencies": { "present", "consistent",
"checked", "error", "mismatches" } }`. `error` is `null` for the absent and
consistent cases and carries the parse failure (same wording as `lock show`)
for a corrupt lock; `dependencies.checked` is `0` when the lock could not be
parsed. The field is additive, so existing consumers of the JSON keep working.
### Event pagination (`sdkt events`)

`soroban-rpc`'s `getEvents` caps every response and returns a top-level
`cursor` for continuation. By default `sdkt events` fetches exactly one page
— the historical behaviour, with the same wire request and output shape as
before — and, when that page stops at a page boundary, prints a notice with
the cursor needed to continue (stdout for pretty output, stderr for `--format
json` so stdout stays parseable JSON).

```bash
sdkt events <contract-id> --start-ledger 1000 --end-ledger 2000
# Scan checkpoint reached (page not full; more events may or may not exist). Continue with:
#   sdkt events <contract-id> --end-ledger 2000 --cursor <cursor>
```

- `--limit <N>` caps the page size (sent as `pagination.limit`).
- `--cursor <CURSOR>` resumes from a previous run's cursor. A cursor-only
  request must omit `--start-ledger`; combining them is rejected before
  any RPC call. `--end-ledger` may still be given: it is a client-side
  bound, enforced locally and never sent on the wire with a cursor.
- `--all-pages [N]` follows the cursor until the pages are exhausted, a
  caller-supplied page cap is reached, or an event passes the RPC's
  `latestLedger`. The cap is explicit and bounded (default 10 pages when no
  value is given, e.g. `--all-pages 25`). When fetching stops at the cap, the
  notice prints the cursor so the run can be resumed later.

Pagination is strictly additive: no change to event decoding, topic
filtering, or ABI-aware value formatting.

### Synchronizing dependencies

`sdkt package update` closes the package loop: `validate → fetch → update → verify`.

It resolves each git dependency's **currently available** commit via `git ls-remote`
against its declared URL (no checkout, no clone in `--check`/`--dry-run`), then:

- **`rev`** — immutable and already pinned; never updated. Reported as `pinned (rev)`.
- **`tag`** — resolves the tag's current commit; if it differs from the lock, the
  cache is refreshed and the lock is rewritten.
- **`branch`** — fetches the latest branch head, updates the cache, and rewrites the
  lock.
- **local `path`** — no remote; reported `unchanged`.

Flags:

- `--check` — report available updates only; **does not** fetch or rewrite the lock;
  exits 0 (non-zero is reserved for hard errors like a missing lock or invalid manifest).
- `--dry-run` — compute everything and preview what would change; the cache and lock
  are left untouched.
- `--format pretty|json` — `json` emits `{"checked","updated","unchanged","changes":[...]}`.

On success the lock records the new `commit_sha`, `resolved_reference`, `cache_location`,
and `integrity` for git deps — contract entries, artifact hashes, and deploy order are
preserved. Clear errors are produced for: missing cache, git unavailable, invalid
manifest, missing lock, detached branch, unknown reference, and network failure.

### Version-constrained dependencies

A git dependency may declare an optional semver `version` constraint instead of a
fixed `tag` / `branch` / `rev`:

```toml
[dependencies.math]
git = "https://github.com/org/math"
version = ">=1.0, <2"
```

When `version` is set **without** an explicit ref, `sdkt package fetch` / `sdkt package
update` resolve the **highest remote tag that satisfies the constraint** (via
`git ls-remote --tags`; offline for local remotes) and materialize / lock that exact
tag. `--check` reports `constraint unsatisfied` when no tag matches. An explicit
`tag` / `branch` / `rev` always takes precedence and the constraint is ignored
(mirroring how `rev` / `path` deps bypass version resolution). The lock records the
resolved `version` for audit. This reuses the existing fetch / cache / lock
infrastructure; the only new logic is a single pure `VersionResolver`.

### Offline packaging & publish readiness

`sdkt package pack` bundles the **fully resolved** project into a portable,
network-free artifact so it can be reconstructed and rebuilt on another machine
without contacting any remote:

- the manifest (`.sdkt.toml`),
- the lockfile (`sdkt.lock`),
- the cached git dependency checkouts under `.sdkt-cache/git/<cache_key>`.

Each artifact carries a `package.json` descriptor (`PackageBundle`) recording the
package `name`/`version`, the chosen `format`, the `sdkt.lock` sha256, and a
per-dependency entry (`source`, `git_url`, `commit_sha`, `integrity`,
`cache_key`, `version`) so the bundle can be verified offline.

Flags:

- `--out <DIR>` — output directory (default `./dist`).
- `--format tar.zst|dir` — `tar.zst` writes a compressed tarball
  `<out>/<name>-<version>.tar.zst`; `dir` writes a directory tree
  `<out>/<name>-<version>/`. Any other value is rejected with a clear error.

**Pack preconditions:** every git dependency declared in the manifest must
have a cached checkout under `.sdkt-cache/git/<cache_key>`. If a declared
dependency's checkout is missing, `sdkt package pack` exits non-zero with a
`git dependency '<name>' is declared but its checkout is not cached ...` error
and writes no descriptor — the bundle never claims a dependency it does not
contain.

`sdkt package publish --dry-run` validates **publish readiness** using the
existing manifest/lock/cache/integrity infrastructure. It detects missing cache,
lock drift, integrity mismatch, commit mismatch, reference change, and invalid
package state — all read-only, no network, nothing is published. `--broadcast` is
explicitly opt-in and is rejected because no registry source is defined; the
workflow remains fully offline.

Round-trip: `sdkt package unpack <artifact> --dest <dir> --verify` reconstructs the
bundle (manifest, lock, cached git checkouts) and verifies it reproduces the
original `sdkt.lock` sha256 and per-git-dependency integrity exactly;
`sdkt package verify-bundle <dir>` re-checks an existing tree, for example after a
mutation. Verification exits non-zero when the lock changed, a checkout is missing
or has a different tree, or a tracked file inside a checkout was modified. No
hashing or git logic is duplicated; the same `compute_dependency_integrity` /
`git_cache_key` primitives are reused.

`--format pretty|json`. `verify-bundle` accepts `--descriptor <package.json>`
(default `<dir>/package.json`) and `--format pretty|json`; its JSON report carries
the descriptor summary (`schema`, `name`, `version`, `format`, `lock_sha256`,
`dependencies`) plus `verified`.

require the local WASM bytes.

After a successful deploy, sdkt verifies the deployed contract by comparing
its on-chain WASM hash against the artifact bytes already in memory (the same
read-only check `sdkt verify` runs; no second file read, no new RPC calls
beyond what `verify` already makes). Pretty output prints
`Verified: on-chain WASM hash matches local artifact ✓`; `--format json`
gains an additive `verification` object
(`{"status": "verified", "onChainWasmHash": "...", "localWasmHash": "..."}`).
A failed verification is NOT a deploy failure — the upload and create
transactions have settled — but it is loud and machine-catchable: a hard
warning on stderr naming both hashes, `"verification": {"status": "failed",
"reason": ...}` in JSON, and exit code **3** (distinct from 0 success, 1
deploy/IO failure, 2 usage error). The same applies when the contract cannot
be read on-chain yet (e.g. not yet visible); re-run
`sdkt verify <contract-id> --wasm <file>` to re-check. `--no-verify` skips
the check entirely — behavior identical to before, with no extra RPC
round-trip — and reports `"verification": {"status": "skipped"}` in JSON.
`sdkt project deploy` verifies every contract it deploys the same way
(one `verification` entry per deployed alias; contracts skipped via
`--skip-deployed` are not re-verified) and also exits 3 when any
verification fails after an otherwise successful deploy.

## Building selected packages

`sdkt build --package <ALIAS>` restricts the build to an allow-list. The build
set is each named alias plus every alias it transitively `depends_on` /
`deploy_after`, in the workspace's resolved build order; an unselected contract
is never built and its WASM artifact is never touched. The flag is repeatable.
An unknown alias fails before any build starts, naming the alias and the known
aliases. Pretty mode prints the selected set (in build order) before building;
`--format json` includes it as `selected`.

```bash
# token has no dependencies, so only token is built
sdkt build --package token

# router depends on vault, and vault depends on token: the closure
# builds token -> vault -> router, in that order
sdkt build --package router

# repeat the flag to select more than one root
sdkt build --package token --package oracle
```

A `--package` build regenerates `sdkt.lock` from the built subset and says so.
Entries for unselected contracts already in an existing lock are preserved, so a
partial build never silently drops them.

## Network Profiles

Saved profiles may also carry endpoint-specific connection policy:

```bash
sdkt network add slow \
  --rpc-url https://rpc.example \
  --passphrase "Test SDF Network ; September 2015" \
  --timeout-secs 60 \
  --pool-max-idle-per-host 20
sdkt network show slow
```

`--timeout-secs` and `--pool-max-idle-per-host` are optional and are omitted
from older profile files. The effective RPC policy uses the profile values
when present, while `.sdkt.toml` and built-in defaults remain the fallback.

### Checking an RPC profile

`sdkt network check <name> [--format json]` performs read-only RPC checks against
the saved profile. It checks ledger reachability and node health, then asks the
endpoint for its network identity with `getNetwork`. The output shows the
profile's configured passphrase beside the endpoint-reported passphrase and
warns when they differ; an available Friendbot URL is shown as well. A mismatch
is advisory and does not change the profile or the command's exit status.

Some RPC providers do not implement `getNetwork`. In that case the command
still reports reachability, health, latest ledger, and protocol version from
the other RPC checks, and labels the identity fields as not reported. JSON
output keeps the existing `profile`, `rpc_url`, `reachable`, `status`,
`latest_ledger`, `protocol_version`, and `error` keys, and adds
`configured_passphrase`, nullable `endpoint_passphrase`, nullable
`friendbot_url`, and nullable `network_info_error`. Only an unreachable or
unhealthy endpoint causes a non-zero exit; failure of the optional identity
query does not.

### Capturing a network profile

`sdkt network capture [--network testnet] [--out network-profile.json]` captures the live
network configuration (protocol version, ledger sequence, cost tables, and resource limits)
into a fuzz `NetworkProfile` JSON file that `sdkt fuzz campaign --profile` can later consume.
It resolves its target exactly like `diagnose` (`--network`, or `--rpc-url` /
`--network-profile` / `.sdkt.toml` defaults), fetches the configuration with read-only RPC
calls, converts it, validates it, and writes the file. The command never signs, submits, or
deploys. A partial capture is still written with status `INCOMPLETE` (naming the unavailable
parameters) and exit 0 — the downstream consumer is what refuses incomplete profiles. An
unreachable endpoint or RPC error fails with a non-zero exit and writes no file. `--format json`
prints the same status report (network, protocol version, ledger sequence, status,
unavailable parameters) as JSON.

Every RPC command (`inspect`, `verify`, `health`, `storage`, `events`, `account`,
`tx`, `fee`, `wasm`, `deploy`, `project deploy`) accepts the same three optional
flags for selecting / overriding the network endpoint:

| Flag | Meaning |
|------|---------|
| `--network-profile <NAME>` | Use a saved profile (see `sdkt network`). Loads its RPC URL + passphrase. |
| `--rpc-url <URL>` | Explicit RPC endpoint; overrides the profile and `.sdkt.toml`. |
| `--network-passphrase <PASSPHRASE>` | Explicit network passphrase; overrides the profile and `.sdkt.toml`. |

**Resolution precedence (highest wins):**

```
explicit --rpc-url / --network-passphrase
        > --network-profile <NAME>
                > .sdkt.toml [network]
                        > NetworkConfig::default()   (testnet)
```

`tx sign` is excluded — it is offline signing and takes only `--network` for the
signature hash. Commands invoked without these flags behave exactly as before.

## Token inspection

`sdkt token info <CONTRACT_ID> [--format json]` inspects a deployed contract
as a SEP-41 token. It fetches the contract's WASM (via `inspect` +
`getWasmBytecode`) and classifies each of the 11 SEP-41 methods
(`name`, `symbol`, `decimals`, `total_supply`, `balance`, `allowance`,
`transfer`, `transfer_from`, `approve`, `burn`, `mint`) from the contract
spec by name **and** signature (account parameters are `address`, amounts
are `i128`, `approve` takes `expiration_ledger: u32`). The presence of a
method is `present`, `absent`, or `signature_mismatch` (right name, wrong
signature) — presence comes from the spec only, never from a simulation
result.

`is_token` is true only when the four metadata methods (`name`, `symbol`,
`decimals`, `total_supply`) are present with matching signatures. Their
values are read by read-only simulation (no-arg, no-auth calls, never
signed or submitted). The other seven methods are never simulated — not
`balance`/`allowance`, and not the state-changing methods. A metadata
value whose simulation fails is reported as `unavailable` with the reason;
that never changes the presence verdict or `is_token`.

Exit codes: 0 for a classified contract (token or not), 2 when the
contract's WASM cannot be fetched or its spec cannot be parsed — an
undecodable or missing contract is never reported as "not a token".

```bash
sdkt token info CAAA... --network testnet
# Token info for CAAA...
#   is_token: true
#   SEP-41 methods:
#     name           present
#     symbol         present
#     decimals       present
#     total_supply   present
#     balance        present
#     ...
#   Metadata:
#     name:          "My Token"
#     symbol:        "MTK"
#     decimals:      7
#     total_supply:  1000000000

sdkt token info CAAA... --network testnet --format json
# {"contract":"CAAA...","is_token":true,"methods":[{"name":"name","presence":"present"},...],
#  "metadata":{"name":{"value":"My Token"},"symbol":{"value":"MTK"},
#  "decimals":{"value":7},"total_supply":{"value":"1000000000"}}}
```

`total_supply` is emitted as a decimal string in JSON because an `i128`
does not fit a JSON number safely. The command takes a bare contract ID;
`@alias` resolution is not supported.

## Batch calls

`sdkt call <CONTRACT_ID> --batch <FILE>` runs several read-only calls in
one command. FILE contains a JSON array of entries:

```json
[
  { "function": "name" },
  { "function": "symbol", "key": "token_symbol" },
  { "function": "balance", "args": ["address:G..."] },
  { "function": "allowance", "args_json": ["[\"G...\", \"G...\"]"] }
]
```

Each entry names a `function` and optionally `args` (the same `TYPE:VALUE`
syntax as `--args`) and `args_json` (the same JSON-array syntax as
`--args-json`). `key` names the result key in the output and defaults to
the function name; keys must be unique across the batch. Calls run
sequentially in file order through the same read-only simulation and
ABI-decoding path as a single `sdkt call` — nothing is signed, submitted,
or otherwise state-changing.

With `--format json` (the default in batch mode), one JSON object is
printed once at the end, mapping each key to its decoded result — the same
decoded display string a single call prints. `--format pretty` prints one
labeled section per entry instead.

The token-metadata example below reads `name`, `symbol`, `decimals`, and
`total_supply` from a SEP-41 token in a single command:

```json
[
  { "function": "name" },
  { "function": "symbol" },
  { "function": "decimals" },
  { "function": "total_supply" }
]
```

```bash
sdkt call CAAA... --batch token-meta.json --network-profile testnet --abi-contract CAAA...
# {"name":"\"My Token\"","symbol":"\"MTK\"","decimals":"u32(7)","total_supply":"i128(1000000000 hi=0, lo=1000000000)"}
```

Validation failures are usage errors (exit code 2) naming the offending
entry by its 0-based index: malformed JSON, a missing `function`,
duplicate keys, and an unknown function name (when `--abi` or
`--abi-contract` is given). Duplicate keys are rejected before any network
call is made. The first entry whose simulation fails stops the batch with a
non-zero exit naming its index and function, and no result object is
printed. `--batch` is mutually exclusive with the positional `FUNCTION`
and with `--args` / `--args-json`; it is not available on `sdkt invoke`.

## Shell completions

`sdkt` can emit shell completion scripts for the major shells. This is the
fastest way to discover subcommands and flags.

```bash
sdkt completions bash       # bash
sdkt completions zsh        # zsh
sdkt completions fish       # fish
sdkt completions powershell # powershell
sdkt completions elvish     # elvish
```

Pipe the output to a file your shell reads at startup (see the README
"Shell completions" section for per-shell install paths). Tab-completion then
covers commands, subcommands, and flag names.

## Doctor

`sdkt doctor` runs baseline diagnostic checks on the sdkt environment and the
current project. It is fully offline and safe to run anywhere.

```bash
sdkt doctor              # human-readable output
sdkt doctor --json      # machine-readable output
```

Checks included in the core:

| Check | ID | Meaning |
|-------|----|---------|
| sdkt runtime | `sdkt-runtime` | confirms the binary is running and reports its version |
| Rust toolchain | `rust-toolchain` | verifies `cargo` and `rustc` are on `PATH` |
| WASM build target | `wasm-target` | verifies a Soroban WASM target is installed via `rustup` |
| Project config | `project-config` | validates `.sdkt.toml` and the `[contracts]` dependency graph when inside a project |

Exit codes:

- `0` — all checks passed, or only warnings (non-fatal)
- `1` — at least one check failed (e.g. invalid config, missing WASM target)

Warnings are never fatal. The JSON output contains no secret material.

## tx validate

`sdkt tx validate --envelope <xdr|file>` parses an envelope and runs
structural checks (fee, sequence, operations) fully offline. With
`--verify-signatures` it also verifies the envelope's signatures against
one or more named signers:

```bash
sdkt tx validate --envelope signed.xdr --verify-signatures \
  --signer GABC... --signer GDEF...
```

`--signer` is repeatable and takes a `G...` public key; a public-key-only
signer is used, so no secret material is ever accepted or read in this
path. Passing an `S...` secret or an unparseable value as `--signer` is a
usage error (exit 2) that does not name the value, so `sdkt`'s own diagnostic never contains the secret. That is no promise about anything outside `sdkt`: a shell with tracing enabled can log the full command before `sdkt` runs, so do not put a secret on the command line. `--verify-signatures` without at least one `--signer` is also a usage error (exit 2). Duplicate
`--signer` values are deduplicated: each distinct key is reported once.

Each named signer is reported as `VALID`, `MISSING`, or `INVALID`. A
signer is `VALID` when at least one signature whose hint (the last four
bytes of the public key) matches the signer verifies against the
envelope hash; `MISSING` when no signature carries the hint; `INVALID`
when hint-matching signatures exist but none verifies. Signatures are
never consumed, and two keys that share a hint are evaluated
independently: with a hint collision, both keys are `VALID` when both
signatures are present, and the key whose signature is absent is
`INVALID` (not `MISSING`), because its hint matches a signature that
does not verify. Signatures whose hint matches no named signer are
listed as `UNMATCHED` (by envelope index and hex hint) for information
only; they never affect the exit code. For a fee-bump envelope only the
outer signatures are considered.

The network is resolved from the usual flags (`--network`,
`--network-profile`, `--network-passphrase`); only the passphrase
matters, and no RPC call is made, so verification works fully offline
and with an unreachable RPC endpoint. The default network is testnet and
the output names the network used. A signature made for a different
network does not verify (`INVALID`).

Exit codes: `0` when structural validation passes and every named
signer is `VALID`; `1` when structural validation fails, any signer is
`MISSING` or `INVALID`, or the envelope hash cannot be computed. When
structural validation fails, the structural report is printed unchanged
and no `Signatures:` section appears. `--format json` adds a
`signatures` array (`address`, `hint`, `status`, `candidates`) and an
`unmatched` array (`index`, `hint`) plus the `network`.

## tx status

`sdkt tx status <HASH>` looks up a transaction by hash and reports its
settlement status. It is read-only: it never signs, submits, or re-submits
anything. Without `--wait` it performs exactly one `getTransaction` lookup;
with `--wait` it polls until settlement, with the same `--timeout` /
`--interval` semantics as `tx submit --wait`.

Exit codes: `0` when the status is `SUCCESS` (or `PENDING` without
`--wait`), `1` when `FAILED`, `2` when `NOT_FOUND` or on a usage error
(malformed hash, unreadable response, wait timeout).

```bash
# Success: prints the status, the hash, and the decoded TransactionResult.
sdkt tx status aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
# Status: SUCCESS
# Hash: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
# Ledger: 100
# Result:
#   {
#     "fee_charged": "100",
#     "result": { "tx_success": [...] },
#     ...
#   }

# Failed: exit 1, with the error code and the failure diagnostic events
# from the result metadata where present.
sdkt tx status bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb
# Status: FAILED
# Hash: bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb
# Ledger: 101
# Error: tx_failed
# Result:
#   ...
# Diagnostics:
#   AAAA...

# Not found: exit 2.
sdkt tx status cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc
# Status: NOT_FOUND
# Hash: cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc

# Pending without --wait: exit 0 — the transaction has not failed, the
# operator only asked whether it settled yet. With --wait the command
# returns once the transaction settles and reports the settled status.
sdkt tx status dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd
# Status: PENDING
# Hash: dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd

# JSON output: one object with hash, status, and the decoded result
# (result_meta where present).
sdkt tx status aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa --format json
# {"hash":"aaaa...","status":"SUCCESS","result":{...},"result_meta":{...}}

# ABI-aware decoding of the invoke return value, reusing the tx simulate
# path (--abi and --abi-contract are mutually exclusive).
sdkt tx status aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa --abi ./contract.wasm
# Status: SUCCESS
# ...
# Decoded Result: u32(42)
```

A malformed hash (anything other than 64 hexadecimal characters) exits 2
naming the problem before any RPC call is made. A corrupt `result_xdr` is
an error naming the hash, never a silent empty result.

## WASM cache

`sdkt wasm cache` manages the local WASM metadata cache (see the
`SDKT_CACHE_DIR` note under `wasm metadata`). Four actions:

```bash
# Aggregate stats for a network: entry count, metadata and WASM byte totals.
sdkt wasm cache info --network testnet

# Enumerate the individual entries for a network, one per cached contract.
sdkt wasm cache list --network testnet
# Cached WASM entries (2):
#   HASH ...                                                              WASM       META
#   551c5a9c7fd4c4a71e57e9c8a0ece1e7bd506ea065993c63db2dc35516406775   530 B      1.2 KB

# The same entries as a JSON array of structured objects (sizes are raw
# bytes here, and `null` marks a half-pair whose other file is missing).
sdkt wasm cache list --network testnet --format json
# [{"network":"testnet","hash":"551c...","metadata_size_bytes":1229,
#   "wasm_size_bytes":530,"warning":null}]

# Remove one entry by hash (the hash is what `list` shows), or clear the
# whole network cache.
sdkt wasm cache remove 551c5a9c7fd4... --network testnet
sdkt wasm cache clear --network testnet
```

`list` is sorted by hash so the ordering is deterministic. An empty or
not-yet-created cache is a useful empty result (`No cached WASM entries`
pretty, `[]` in JSON), never an error. A malformed `{hash}.json` produces a
per-entry warning (a `⚠` marker in pretty output, a `warning` field in JSON,
and a diagnostic on stderr) while the listing still completes — it never
aborts the whole listing, matching how `wasm metadata` treats cache read
errors as warnings.

## Encode

`sdkt encode` converts a typed value to its base64 XDR representation — the
write-direction counterpart to `sdkt decode`. It is fully offline and useful
for building test fixtures, debugging, and CLI round-trips.

```bash
sdkt encode u32:100
# AAAAAwAAAGQ=

# Verify by decoding back
sdkt encode string:hello | xargs sdkt decode --type ScVal
# {"string": "hello"}

sdkt encode symbol:USD | xargs sdkt decode --type ScVal
# {"symbol": "USD"}

sdkt encode u128:340282366920938463463374607431768211455 | xargs sdkt decode --type ScVal
# {"u128": "340282366920938463463374607431768211455"}

sdkt encode i128:-1000 | xargs sdkt decode --type ScVal
# {"i128": "-1000"}

sdkt encode timepoint:1758000000 | xargs sdkt decode --type ScVal
# {"timepoint": "1758000000"}

sdkt encode duration:86400 | xargs sdkt decode --type ScVal
# {"duration": "86400"}

sdkt encode bytes:000aFF | xargs sdkt decode --type ScVal
# {"bytes": "000aff"}

sdkt encode json:'[1,2,3]' | xargs sdkt decode --type ScVal
# {"vec": [{"u32": 1}, {"u32": 2}, {"u32": 3}]}
```

### Supported types (core subset)

`u32`, `i32`, `u64`, `i64`, `timepoint`, `duration`, `u128`, `i128`, `bool`, `string`,
`symbol` (up to 32 bytes), `bytes`, `address` (Stellar `G...` strkey).

Exactly one value is encoded per invocation; the `TYPE:VALUE` syntax matches
the typed-argument convention used by `sdkt call` and `sdkt invoke`.

`u128` and `i128` accept decimal integers within their full 128-bit ranges.
Their decoded JSON values are decimal strings, preserving all digits.
`bytes` accepts hexadecimal pairs without a `0x` prefix, with either hex
letter case. Surrounding whitespace is trimmed; empty input (`bytes:`)
encodes empty bytes. Leading zero bytes are preserved, and decoded JSON
uses lowercase hex. Pair parsing matches the runtime typed-argument parser,
including its acceptance of a leading `+` in a pair (`bytes:+f` encodes `0f`).

### Composite values (`json:`)

`json:<JSON>` encodes one JSON value, including nested arrays and objects, as a
single `ScVal`: `json:[1,2,3]` is one `Vec`, not three values. The mapping is:
array to `Vec`, object to `Map` with `String` keys (sorted), `null` to `Void`,
`true`/`false` to `Bool`, string to `String`, and an integer to the smallest
fitting `u32`/`u64` (`i32`/`i64` when negative). Floats and integers beyond
the 64-bit range are rejected. Invalid JSON fails with
`invalid JSON in 'json:<input>': <reason>`.

### Unsupported (clear failure)

Other types, such as `vec:`, `map:`, `Option`, `Result`, and UDTs, are
rejected with an error listing the supported types (use `json:` for `Vec`
and `Map`). Malformed values (bad or out-of-range
numbers, invalid bools, invalid strkeys, odd-length or invalid hex) fail
with a message naming the offending value.

## Generate client

`sdkt generate client` produces deterministic, typed Rust call builders from
the ContractSpec of a compiled Soroban contract WASM. The command is fully
offline — it reads a local `.wasm` artifact and emits Rust source.

```bash
# Print the generated client to stdout
sdkt generate client target/wasm32v1-none/release/my_contract.wasm

# Write it to a file
sdkt generate client contract.wasm --output src/client.rs

# Generate a partial client, skipping unsupported functions
sdkt generate client contract.wasm --skip-unsupported --output src/client.rs
```

### Output

Each contract function becomes a `*Call` struct with:
- one typed field per parameter,
- a `NAME` constant with the contract function name,
- an `args()` method encoding the call as `TYPE:VALUE` strings — the same
  typed-argument convention accepted by `sdkt call` and `sdkt invoke`,
- a `<Function>Output` type alias mirroring the return type.

The output is deterministic: the same input WASM always produces
byte-identical source, suitable for checking generated files into a repo.

### Supported types (core subset)

Parameters and single return values of these primitive types are supported:
`u32`, `i32`, `u64`, `i64`, `bool`, `address`, `string`, `symbol`, `void`
(no return).

### Unsupported (clear failure)

By default, any other type — UDTs, `Option`, `Result`, `Vec`, `Map`, `Tuple`,
`BytesN`, `Val`, multiple return values — aborts generation with an error naming
the function, the type, and the position (parameter or return). Nothing partial
is emitted. A WASM without a `contractspecv0` section is rejected as
"not a Soroban contract".

### Partial generation (`--skip-unsupported`)

Pass `--skip-unsupported` to generate call builders for the supported subset of
functions instead of aborting the entire command:
- Supported functions are generated in original spec order.
- Skipped functions and their specific reasons are listed deterministically in
  the generated file header comment.
- If all functions in the contract are supported, output is identical to the
  default (no-flag) output.
- If all functions in the contract are unsupported, valid non-crashing output is
  produced with an empty `contract_functions()` and an explanatory header.

## Fuzz

`sdkt fuzz` provides Soroban-aware deterministic fuzzing for release assurance. It is fully offline and read-only: contracts execute in an isolated in-memory host environment without touching the network.

### Campaign

`sdkt fuzz campaign [<WASM>]` (or `sdkt fuzz campaign --config <FILE>`) runs a deterministic fuzz campaign against a compiled contract.

**Syntax:**

```bash
sdkt fuzz campaign contract.wasm \
  --seed 42 \
  --cases 100 \
  --function increment \
  --auth correct-auth \
  --artifact-dir ./sdkt-fuzz-artifacts \
  --expect-success increment \
  --expect-error invalid:Auth:6 \
  --replay \
  --format json
```

Or from a checked-in TOML definition file:

```bash
sdkt fuzz campaign --config fuzz.toml
```

**Arguments and flags:**

| Flag | Default | Meaning |
|------|---------|---------|
| `<WASM>` | *required unless `--config` supplies `campaign.wasm`* | Path to the compiled contract WASM file. When both `<WASM>` and `campaign.wasm` are provided, they must match (mismatch exits `2` naming both values) |
| `--config <FILE>` | none | Path to a TOML campaign definition file. Precedence: explicit CLI flags override config values; config values override defaults |
| `--seed <N>` | `0` | Deterministic seed (u64). Same seed produces identical test case sequence across runs |
| `--cases <N>` | `100` | Number of test cases to execute (must be `>= 1`; `--cases 0` is a usage error, exit `2`) |
| `--function <NAME>` | all | Restrict the campaign to one exported contract function (if no runnable function matches, exits `2` without writing clean evidence) |
| `--artifact-dir <DIR>` | `./sdkt-fuzz-artifacts` | Directory where finding artifacts are written |
| `--auth <MODE>` | `no-auth` | Authorization mode per test case: `no-auth`, `correct-auth`, or `wrong-auth`. See the sdkt-fuzz docs for exact semantics |
| `--expect-success <FN>` | none | Declare that function `<FN>` must succeed (repeatable). Violations produce `RETURN_MISMATCH` or `UNEXPECTED_ERROR` findings |
| `--expect-error <FN:TYPE:CODE>` | none | Declare that function `<FN>` must fail with error type `<TYPE>` and code `<CODE>`, e.g. `--expect-error bump:Auth:6` (repeatable) |
| `--sequence-length <N>` | off (`2` when active) | Number of invocations in each generated multi-step sequence (`>= 2`; must be paired with `--sequence-every`) |
| `--sequence-every <N>` | `0` (disabled) | Execute every `N`-th case (`case_number % N == 0`) as a multi-step sequence (`>= 1`; must be paired with `--sequence-length`) |
| `--replay` | false | Replay every written artifact to verify determinism and reproduce findings |
| `--format <FORMAT>` | `pretty` | Output format: `pretty`, `json`, or `jsonl` |

**Expectation declarations:**

- `--expect-success <FN>` — declare that a function must always return successfully. If a case returns an error or value mismatch, it produces a finding.
- `--expect-error <FN:TYPE:CODE>` — declare that a function must fail with a specific error. Format: `FunctionName:ErrorType:ErrorCode`. Example: `--expect-error transfer:Auth:6` means the `transfer` function must fail with `ContractError{Auth, 6}`.
- A function may have only one expectation; declaring it with both flags is a usage error (exit 2).
- Malformed declarations are usage errors (exit 2).

Campaign `--format json` output and the `campaign-evidence.json` file written
to `--artifact-dir` include additive top-level provenance fields:
`schema_version` (`1`), `tool` (`"sdkt"`), and `version` (the build's
`CARGO_PKG_VERSION`). Older evidence without these fields remains readable;
its missing provenance is treated as unknown.

**Campaign config file (`--config <FILE>`):**

`sdkt fuzz campaign --config fuzz.toml` loads campaign settings and expectations from a TOML file with `[campaign]` and `[[expect.success]]` / `[[expect.error]]` tables:

```toml
[campaign]
wasm = "target/wasm32v1-none/release/contract.wasm"
seed = 42
cases = 100
function = "increment"
auth = "correct-auth"

[[expect.success]]
function = "increment"

[[expect.error]]
function = "withdraw"
type = "Auth"
code = 6
```

- **Precedence:** explicit CLI flags override config values; config values override built-in defaults (`seed = 0`, `cases = 100`, `auth = "no-auth"`).
- **Validation:** unknown keys, missing or malformed TOML files, missing `wasm` from both `<WASM>` and `campaign.wasm`, or a mismatch between positional `<WASM>` and `campaign.wasm` are rejected as usage errors (exit `2`) before any case executes.

**Sequence execution (state carry):**

- By default (when both `--sequence-length` and `--sequence-every` are omitted), every case runs a single invocation against a fresh baseline (`sequence_every = 0`).
- Passing `--sequence-length <L>` and `--sequence-every <E>` together exercises state carry across invocations: every `E`-th case (`case_number % E == 0`, starting at `case0000`) executes an ordered sequence of `L` calls to the selected function, carrying contract instance and data storage forward from step to step and building per-step authorization entries under `--auth`. All other cases run as single-step invocations.
- Both flags must be supplied together: passing only one is a usage error (exit `2`) rejected before any campaign work starts. Values below the engine minimums (`--sequence-length < 2` or `--sequence-every < 1`) are also rejected with exit `2`.
- When sequence mode is active, the campaign summary reports `sequences=<S> single_step=<K>` alongside the standard counters, and finding artifacts record `campaign.sequence_length`, `campaign.sequence_every`, and the minimized multi-step `sequence` array for replay via `sdkt fuzz replay`.

**Output artifacts:**

Finding artifacts are written to `--artifact-dir` as JSON files following the naming pattern `<contract>-<function>-case<NNNN>.json`. Each artifact contains:

- `artifact_hash` — SHA-256 of the canonical artifact JSON (used for deduplication and replay verification)
- `wasm_hash` — SHA-256 of the WASM that produced the finding
- `campaign_seed` — seed used to generate the test case sequence
- `case_id` — zero-based case index in the campaign
- `input` — the typed arguments, seed, and auth mode for this case
- `observed_result` — the actual return value or error from contract execution
- `classification` — the finding type: `Pass`, `ExpectedError`, `ReturnMismatch`, `UnexpectedError`, etc.
- `minimized` — whether the case was minimized
- `complexity` — case complexity before and after minimization
- `observation` — structured error/return data for replay
- `auth_per_step` — authorization entries for each step in a multi-step sequence (if applicable)

**Supported `--format` values:**

| Format | Purpose |
|--------|---------|
| `pretty` | Human-readable report; findings listed with classification and details |
| `json` | Single JSON document: campaign metadata + findings array |
| `jsonl` | JSON Lines: one artifact per line for streaming processing |

**Exit codes:**

- `0` — campaign executed at least one case with no findings
- `1` — campaign produced one or more findings
- `2` — usage / configuration / input error (e.g. `--cases 0`, a `--function` filter matching no runnable function, a contract with no runnable functions, malformed expectation, invalid flags, or unreadable WASM)

### Replay

`sdkt fuzz replay <artifact>` replays a finding artifact against its WASM to verify it reproduces.

**Syntax:**

```bash
sdkt fuzz replay ./sdkt-fuzz-artifacts/contract-increment-case0042.json \
  --wasm contract.wasm
```

**Arguments and flags:**

| Flag | Meaning |
|------|---------|
| `<ARTIFACT>` | Path to the finding artifact (JSON) produced by a campaign |
| `--wasm <WASM>` | *required* — Path to the campaign WASM the artifact was produced from |

**Replay verdict:**

| Exit code | Verdict | Meaning |
|-----------|---------|---------|
| `0` | `REPRODUCED` | The artifact reproduced: same input, same result, finding verified |
| `1` | `MISMATCH` | The artifact did not reproduce: result differs from expected |
| `2` | Usage error | Invalid artifact or WASM path |

**Determinism:**

If `--replay` was used during the campaign, every artifact was automatically replayed to verify determinism. A `REPRODUCED` verdict confirms that the finding can be independently re-executed with the exact same inputs and produce the same result.

### Compare

`sdkt fuzz compare --baseline <BASELINE.json> --new <NEW.json>` diffs two campaign
evidence files (`campaign-evidence.json`, written next to the artifacts by
`sdkt fuzz campaign`) and reports which findings are new, which are fixed, and
which persist — so CI can gate on regressions instead of judging each run in
isolation.

```bash
sdkt fuzz compare --baseline last-week/campaign-evidence.json \
  --new this-week/campaign-evidence.json
# exit 1 when the new run introduced a finding; use it as a CI gate:
#   sdkt fuzz compare --baseline baseline.json --new new.json || exit 1
```

Findings are matched by `artifact_hash` only; a finding in `--new` but not in
`--baseline` is NEW, in `--baseline` but not in `--new` is FIXED, and in both
is PERSISTING. The report groups findings by `reason_code` and `function` and
names each by `case_id`, `function`, and `reason_code`. Differences in seed or
case count are informational (printed in the header), not errors. The two
campaigns must target the same artifact — a different `config.wasm_sha256` is
an error naming both hashes. `--format json` emits one object with `new`,
`fixed`, and `persisting` arrays plus both `wasm_sha256` values.

| Exit code | Meaning |
|-----------|---------|
| `0` | No new findings (including the all-fixed case) |
| `1` | At least one new finding exists |
| `2` | Usage error: unreadable or unparseable evidence file, WASM mismatch |

The command is read-only: it never writes, modifies, or deletes either
evidence file, and it does not run a campaign.

### Artifact directory layout

By default, artifacts are written to `./sdkt-fuzz-artifacts` with this structure:

```
./sdkt-fuzz-artifacts/
├── <contract-hash>-<function-name>-case0000.json
├── <contract-hash>-<function-name>-case0001.json
├── <contract-hash>-<function-name>-case0042.json
└── ...
```

Each JSON file is a complete finding artifact, self-contained and ready for replay.

### Integration with release assurance

`sdkt release-assurance` accepts `--fuzz-evidence <EVIDENCE_JSON>` to attach fuzz evidence to a release report. The release pipeline does not run fuzz campaigns itself; campaigns are run separately (manually or in CI) and the resulting evidence is attached by path.

JSON release-assurance reports append `schema_version` (`1`), `tool`
(`"sdkt"`), and `version` (the build's `CARGO_PKG_VERSION`) to identify the
report schema and producing CLI build. These keys are additive; existing
report fields retain their names, types, and order.

A fuzz evidence file scores `PASS` only when `campaign_completed` is `true`, `case_count > 0`, and `findings` is empty. Evidence with `campaign_completed: false` or `case_count: 0` is never scored as `PASS` — it maps to `ERROR` and fails the release-assurance check.

## Plugin management

A **local, offline-first** plugin store. All operations are local;
there is no hosted registry and no remote source. Plugins are referenced by a
stable `id` declared in their `plugin.toml`.

```bash
sdkt plugin list                                   # list installed plugins
sdkt plugin list --format json                     # JSON output; every plugin subcommand accepts --format json
sdkt plugin init ./path/to/my-rule                 # scaffold a new audit rule project
sdkt plugin show <id>                              # show a plugin's metadata
sdkt plugin install ./path/to/artifact.wasm        # install from a local file
sdkt plugin install ./bundle.sdktplugin            # verify, then install a bundle (reports signed: true/false)
sdkt plugin install ./bundle.sdktplugin --public-key ./pubkey.key               # require a signature from this author key (unsigned is refused)
sdkt plugin remove <id>                            # remove (idempotent)
sdkt plugin update <id> ./path/to/artifact.wasm    # local-only update
sdkt plugin pack ./path/to/plugin-dir --output ./myrule.sdktplugin              # pack into .sdktplugin bundle
sdkt plugin pack ./path/to/plugin-dir --secret-key ./secret.key                 # sign bundle with Ed25519 secret key (32 bytes, raw)
sdkt plugin verify-bundle ./bundle.sdktplugin                                                # verify unsigned bundle integrity
sdkt plugin verify-bundle ./bundle.sdktplugin --public-key ./pubkey.key                      # verify signed bundle against a specific public key
sdkt audit contract.rs --rules <id>                # resolve id → stored artifact
```

`sdkt audit --rules <id>` resolves an installed plugin ID to its stored
artifact; filesystem paths must point to compiled `.so`, `.dylib`, `.dll`, or
`.wasm` plugin artifacts. Passing a directory prints a warning and the audit
continues with the built-in rules.
Installing a `native` plugin prints a warning: native plugins run **unsandboxed**
(unmodified behavior). See `docs/plugins/plugin-authoring.md` for the `plugin.toml`
schema and the install-validation rules.

Store root precedence (lowest → highest): `<cwd>/.sdkt/plugins`,
`<config-dir>/sdkt/plugins`, `$SDKT_PLUGIN_DIR`.

- `--format json` is supported on all read-style commands, every `plugin` subcommand, and on `diff`, `audit`, `deploy`, `init` for scripting / CI.
- `diff --upgrade-safety` and `deploy --deny-breaking` implement the Upgrade Safety Guard (see `ROADMAP.md`).
- **Network Fit.** `sdkt release-assurance` includes a `Network Fit` section (`network_fit` in JSON) that fetches the live network's `ContractMaxSizeBytes` setting via `capture_network_config` and compares it with the candidate artifact's byte size (`PASS` when `size <= limit`, `FAIL` naming both byte counts when `size > limit`, or `SKIPPED` without affecting `release_status` when the network is unreachable or the setting is unavailable).

- **Deploy preflight.** `sdkt deploy --wasm <file> --release-assurance` checks the artifact before identity lookup and upload. Repeat `--preflight-audit <path>` for source audits and `--preflight-fuzz-evidence <file>` for recorded fuzz evidence; `--old-wasm` enables Upgrade Safety. Verification and Contract Health are skipped because the candidate has not yet been deployed on-chain. In JSON mode (`--format json`), the pretty preflight report is routed to stderr so stdout remains parseable JSON. A failure or assurance error aborts the deployment; without the flag the existing flow is unchanged. (Note: assurance inspects the WASM file at the specified path before upload; avoid modifying the candidate file between preflight and upload to prevent TOCTOU discrepancies).
- **Diffing deployed contracts.** `sdkt diff` accepts `--old-contract <C...>` / `--new-contract <C...>` in place of `--old-wasm` / `--new-wasm`: each contract side fetches its on-chain WASM over RPC (the same `inspect` → `getLedgerEntries` composition `verify --upgrade-safety` uses) and the fetched bytes are diffed by the existing `diff_wasm` path. The two sides are independent — a file side and a contract side can be mixed. Contract-ID sides require a network: `--network testnet` (or `futurenet`) for the built-in public endpoints, `--rpc-url <URL>` together with the mainnet passphrase for mainnet — `--network mainnet` alone is rejected because there is no built-in public mainnet RPC endpoint — or a saved `--network-profile <NAME>` (e.g. a stored mainnet profile created with `sdkt network add mainnet --rpc-url <URL> --passphrase "Public Global Stellar Network ; September 2015"`); `--old-contract` conflicts with `--old-wasm` (same for `--new-*`), and each side needs at least one source. A contract ID that does not exist on the network fails with a clear "contract not found" error. Pretty output is unchanged; `--format json` records each side's origin in the additive `old_source` / `new_source` fields (`{"kind": "file", "path": ...}` or `{"kind": "contract", "contract_id": ...}`), which are absent for the classic two-file diff. `--upgrade-safety`, `--max-growth-pct`, and `--max-size-bytes` work with contract-ID sides exactly as with files.

  ```bash
  sdkt diff --old-contract CAE3U7JKESRWZHPEQ72DVNGOQ6WPA7HSPQZL5YV46NPCE4TMUPAGYMEC \
      --new-contract CDLZFC3SYJYDZT7K67VZ75HPJVIEUVNIXF47ZG2FB2RMQQVU2HHGCYSC \
      --network testnet --format json
  ```

- **WASM size policy (opt-in).** `diff` and `release-assurance` accept `--max-size-bytes <N>` (absolute ceiling on the candidate artifact) and `--max-growth-pct <N>` (growth over the baseline). Thresholds are **operator-supplied policy** — SDKT hardcodes no Stellar network limit, and passing a threshold does not assert network-limit compliance. `diff` measures growth against the old side (file or contract); `release-assurance` requires `--previous-wasm` for a growth check and fails with an explicit error when it is missing rather than silently skipping. Violations exit non-zero: `diff` prints the violation on stderr after the report, and `release-assurance` marks the artifact section `FAIL` (so `release_status` becomes `FAIL`). Boundaries are inclusive — a size exactly at the limit or growth exactly at the cap passes. `diff --format json` also reports `size_delta_bytes` (signed) and `size_delta_pct` (one decimal, `null` when the old artifact is zero bytes). Size policy is independent of ABI compatibility: it is refused in combination with `diff --upgrade-safety`, and a size violation never changes an upgrade-safety verdict.

  ```bash
  # Report size change alongside the ABI diff (always on, no flags needed):
  sdkt diff --old-wasm prev.wasm --new-wasm candidate.wasm --format json

  # Fail the build on a >10% growth OR a >128 KiB candidate (your numbers):
  sdkt diff --old-wasm prev.wasm --new-wasm candidate.wasm \
      --max-growth-pct 10 --max-size-bytes 131072

  # Gate a release on the same policy, inside the full assurance report:
  sdkt release-assurance --wasm candidate.wasm --previous-wasm prev.wasm \
      --max-growth-pct 10 --max-size-bytes 131072
  ```

- `audit` implements the static-analysis rules (AUTH-001/002/003/004, MOVE-001, MATH-001, CEI-001). Nested modules are scanned recursively: functions inside `mod` blocks (including a `mod` inside a `mod` and `impl` blocks inside a `mod`) are checked the same as top-level functions, with findings located by their qualified path (e.g. `inner::initialize`). Only modules declared inline in the audited file are scanned; `mod foo;` pointing at another file and `use` declarations are not followed.
- **AUTH-001/AUTH-004 severity follows observed behavior, not the name.** Both rules start from a privileged-name heuristic (`initialize`/`init`, `set_*`/`grant_*`/`revoke_*` prefixes, and the substrings `admin`, `mint`, `burn`, `pause`, `unpause`, `upgrade`, `withdraw`, `configure`, `freeze`, `ban`, `drain`, `set_admin`, `owner_set`, `transfer_ownership`, `change_owner`, `set_auth`), then decide severity from what the function actually does:
  - a method of a `#[contractimpl]` block that performs a recognized state write or an external call and never calls `require_auth()` → **critical** (the unguarded-privilege case);
  - a function that is **not** a `#[contractimpl]` method (a plain `fn` or a method of an un-annotated impl) → **info**: external callers cannot reach it, so authorization is the responsibility of the entrypoint that calls it;
  - a `#[contractimpl]` method that returns a value with no recognized state write or external call → **info**: positive evidence of a read-only accessor (`admin_balance`, `get_paused`), which cannot be a missing-authorization defect;
  - a `#[contractimpl]` method that returns nothing with no *recognized* side effect → **critical**: the write may go through a helper the scanner does not recognize, so the finding stays loud.

  Nothing is deleted — a demotion is a severity change, always visible in the report (pretty, `--format json`, and `--format sarif` agree). `--fail-on`/CI gates keyed to `critical` therefore stop triaging getter noise, while `info` findings remain auditable.
- **`--fail-on <severity>` (opt-in CI gate).** `sdkt audit` exits `0` on findings by default. With `--fail-on critical|warning|info` (case-insensitive) the already-computed severity summary is mapped to the process exit code: exit `1` when any finding is at or above the threshold, after the full report has been printed unchanged — in pretty, JSON, and SARIF output alike. An invalid level is a usage error (exit `2`) raised before any analysis runs. The flag is independent of `--disable`: disabled rules produce no findings and therefore never trip the gate.
- **`--save-baseline <path>` and `--baseline <path>` (ratchet CI gate).** `--save-baseline <path>` persists the current audit report to `<path>` as JSON (`{ "sdkt_version", "rules", "findings", "summary" }`). `--baseline <path>` loads a saved baseline, compares current findings against the baseline (keyed on `rule_id`, `location`, and `message`), and reports `Baseline: <N> known findings`, `New findings: <M>`, and `Resolved: <K>` in pretty mode (or `{ "baseline_total", "new_findings", "resolved_findings", "unchanged_findings", "findings", "summary", "spec_correlated" }` with `--format json`). Exits `1` when new findings are introduced and `0` when current findings are identical to or a subset of the baseline. If the baseline was created with a different `sdkt` version or rule set, a staleness warning is emitted on stderr.
- `audit --list-rules` discovers all registered built-in rules (with id, severity, and description). Supports `--format json` and does not require a source path argument.
- **Health verdict exit codes.** `sdkt health` exits non-zero when the verdict is `critical` (for example, the deployed WASM does not match the file passed with `--wasm`), so a mismatched artifact cannot pass CI or an agent check that only reads the exit code. `at_risk` remains non-blocking (exit 0), matching how `release-assurance` treats it.
- **`sdkt-agent`.** A separate binary that turns a plain-language request into a validated, read-only `sdkt` invocation: `sdkt-agent "check health of contract C… on testnet"`. It resolves the capability from the registry, pins an explicit testnet endpoint for network-touching checks, refuses mutating capabilities and mainnet targets outright, and never guesses on an ambiguous request. `--format json` emits a versioned result document; the default output is a six-line summary. Full guide — build, capability surface, ambiguity and refusal codes, artifact roles, mutation boundary, network policy, result semantics, troubleshooting: [sdkt-agent](agent.md).
- **Agent capability registry (`sdkt_core::registry`).** The CLI's capabilities are described in one machine-readable table — command path, required/optional arguments, output formats, exit semantics, network requirement, safety class, and an evidence level — exportable as a versioned JSON manifest (`sdkt_core::registry::to_json()`). It is metadata about existing commands only: nothing is executed and no new CLI surface is added. Mutating capabilities (deploy, invoke, tx sign/submit, storage extend/restore, project deploy, identity fund) are marked `requires_confirmation` and are never marked verified by a read-only audit. Adding a capability means appending one `Capability` entry and keeping the parity test green; see the module docs for the rules the tests enforce.
- **`sdkt build --format json`.** Emits a single JSON document on stdout: `{"success": true, "artifacts": [{"alias", "path", "wasm_artifact"}]}` on success, or `{"success": false, "error": "..."}` with a non-zero exit on failure. The advisory `sdkt.lock` report is written to stderr so stdout stays parseable; the default pretty output is unchanged.
- **Contract metadata (`contractmetav0`).** `sdkt wasm inspect <file.wasm>` decodes the `contractmetav0` custom section and prints a `Contract Metadata` block of `key = value` entries (for example the `rsver`, `rssdkver`, and `cliver` provenance keys) in section order, with duplicate keys preserved. A WASM without the section prints `Contract Metadata (0):` followed by `(none)`. With `--format json` the entries appear as the additive `metadata.contract_meta` array of `{ "key": ..., "value": ... }` objects — an empty array when the section is absent — alongside the existing `metadata` keys, which are unchanged. A malformed `contractmetav0` payload is reported as a classified error rather than a panic.
- `sdkt wasm metadata --contract <id>` reports the same entries for the deployed contract, from the fetched (or cached) WASM bytes: pretty output gains the identical `Contract Metadata` block, and `--format json` gains an additive top-level `contract_meta` array alongside the existing inspection keys, which are unchanged. It is empty when the deployed WASM carries no `contractmetav0`.
- **Workspace preflight gate (`sdkt project deploy --release-assurance`).** Runs `run_release_assurance` for every contract that will actually deploy (after `--skip-deployed` filtering) **before** the upload loop starts, and aborts the entire workspace deploy (exit `1`, uploading nothing) if any contract's preflight returns `FAIL` or `ERROR`. For each deploying contract, the preflight runs **Artifact** (against the resolved `wasm_artifact`), **Security** (against the contract's source directory `path`), and **Upgrade Safety** (fetching the previously deployed WASM bytes via `inspect_contract` → `get_wasm_bytecode` into a temporary file when a deployment record exists for that alias, or marking Upgrade Safety `SKIPPED` when no prior record exists). **Fuzz Evidence**, **Verification**, and **Contract Health** are `SKIPPED` by construction during preflight because Verification and Contract Health are post-deploy checks and Fuzz Evidence requires per-contract evidence mapping. Without `--release-assurance`, `sdkt project deploy` behavior and output are unchanged.
- **Mainnet safety.** Mutating commands (`tx submit`, `invoke`, `deploy`, `project deploy`) refuse to target mainnet unless you explicitly select the network — via `--network-profile`, `--rpc-url`, or `--network-passphrase`. A testnet-default passphrase pointed at a mainnet endpoint is rejected before any request is sent, protecting against signing for the wrong network.

## Fuzz expectation declarations

`sdkt fuzz campaign` accepts repeatable `--expect-success <FN>` and
`--expect-error <FN:TYPE:CODE>` declarations. A function may have one
expectation; declaring it with both flags is a usage error that exits 2 and
names the conflicting function. A single valid declaration keeps its existing
campaign behavior. Malformed `--expect-error` declarations also remain usage
errors.

### Resource-limit findings (opt-in)

By default a budget-class host error under `--expect-success` is reported as
`UNEXPECTED_ERROR` — indistinguishable from a logic error in the finding
stream. `--resource-limit-is-finding` opts the run into the oracle's
RESOURCE_LIMIT rule: budget-class failures under a declared `Success`
classify as `RESOURCE_LIMIT` findings instead. The default is **off** —
resource exhaustion is an outcome, not a verdict — so campaigns without the
flag behave exactly as before. The rule is run-level: it applies to every
expectation declared for the run.

The flag alone cannot produce a budget error, because the default campaign
budget is generous. `--budget-capped <CPU:MEM>` exposes the engine's
deterministic capped-budget plan (`BudgetPlan::Capped`, the purpose-built
budget-exhaustion path — deterministic and reproducible but **not**
network-faithful), e.g. `--budget-capped 1:1` caps every case at one CPU and
one memory unit so a declared `Success` hits the host's `Budget` error:

```bash
# Without the rule: a capped-budget error under --expect-success is
# UNEXPECTED_ERROR, as before.
sdkt fuzz campaign contract.wasm --cases 1 --function hello \
    --expect-success hello --budget-capped 1:1
# FINDING … UNEXPECTED_ERROR

# With the rule: the same campaign reports RESOURCE_LIMIT instead.
sdkt fuzz campaign contract.wasm --cases 1 --function hello \
    --expect-success hello --budget-capped 1:1 --resource-limit-is-finding
# RESOURCE_LIMIT
```

The campaign evidence records whether the rule was enabled: a run that used
it carries `"resource_limit_is_finding": true` in `campaign-evidence.json`,
while default-off runs omit the field entirely (byte-identical to pre-flag
evidence). The capped budget itself is already part of the recorded
campaign configuration (`config.environment.budget`).

## Configuration validation (`sdkt config validate`)

`sdkt config validate` checks a project's `.sdkt.toml` offline (no RPC calls, no network access) in two stages so CI can gate on configuration problems before building or deploying:

1. **Stage 1 — Schema validation on the raw TOML file (`validate_config_schema`):** Parses `.sdkt.toml` as raw `toml::Value` and flags malformed TOML, duplicate tables, and unknown keys across top-level sections (`network`, `decode`, `storage`, `contracts`, `dependencies`, `package`), reporting both section and key name. `[package]` unknown keys are allowed by design for forward compatibility. If Stage 1 finds any problem (or if value-type deserialization fails), the CLI prints the problems and exits `1` without running Stage 2.
2. **Stage 2 — Semantic validation on `DevKitConfig` (`DevKitConfig::validate(&self, base_dir)`):**
   - **Numeric ranges:** `storage.max_entries > 0`, and `network.timeout_secs` / `network.pool_max_idle_per_host` (when set) `> 0`. `decode.max_depth = 0` is valid (unlimited).
   - **Contract paths:** Every `[contracts.<alias>].path`, resolved relative to the directory containing `.sdkt.toml` (or used as-is if absolute), must exist on disk and contain a `Cargo.toml`.
   - **Dependency combinations:** Validates `[dependencies]` via `validate_dependencies(base_dir, config)` (mutually exclusive `path`/`git`, required git ref or valid semver `version` requirement, path existence).
   - **Deploy order graph:** Validates `[contracts]` via `validate_project(config)` when `contracts` is non-empty (cycles, unknown dependencies, self-dependencies, duplicate dependency entries across `deploy_after` and `depends_on`).

**Exit codes & formats:**
- `0` — Configuration is valid (or no `.sdkt.toml` exists, in which case defaults apply).
- `1` — One or more schema or semantic problems were found.
- `--format json` prints `{"valid": bool, "problems": [{"section": "...", "key": "...", "message": "..."}]}`.

## Error Handling

1. All subcommands return `Result<(), Box<dyn std::error::Error>>`.
2. Library-level errors (`RpcError`, `DecodeError`, `WasmError`) are bubbled up to the CLI.
3. The CLI uses `eprintln!` to print human-readable errors and exits non-zero on fatal errors to ensure correct bash piping behavior.
